# Ведение PR до мержа

Цикл координатора, записанный один раз, чтобы любой агент вёл PR так же. Правила команды — `TEAM.md`, QA — `design/QA.md`.
Цель — **один учитываемый прогон QA на PR**. Каждый лишний круг стоит ~20 минут CI.

## 1. Перед PR (локально, в ветке)

1. `git fetch origin main && git merge origin/main` — merge, не rebase запушенной ветки.
2. Если трогали токены — `npm run tokens`. Если трогали генератор — `node --test scripts/tokens/dtcg.test.mjs`.
3. `npm run typecheck && npm run lint && npm run build-storybook`.
4. `CHROME_PATH=/opt/pw-browsers/chromium npm run qa -- --no-docker --changed` (= `qa:changed`) — ошибок 0: только истории, задетые веткой; при правке токенов, глобальных стилей, `scripts/qa/` — сам переходит на полный прогон. Визуальная регрессия локально не считается. CI гоняет всё.
5. `npm run flow-diff` — расхождений 0.
6. Если меняли истории с `play` — `CHROME_PATH=/opt/pw-browsers/chromium npm run test-storybook`. Play-история по умолчанию `no-visual` (эталона нет); нужен скриншот (play только ставит фокус или проверяет геометрию) — тег `visual` и эталон через baseline.
7. `/code-review` по диффу ветки. Находки уровня «баг» — исправить до PR.

В worktree агента нет `node_modules` → `npm ci` (симлинк на основной checkout ломает Vite: `server.fs.allow`).

## 2. PR

- Открывать **готовым, не draft**, только после зелёных локальных проверок. `ready_for_review` не запускает учитываемый QA повторно.
- Тело PR: «Что сделано», «Проверки» (числа из прогонов), «Передача» (что не сделано, кто делал). Ссылка на issue: `Closes #N` или `Refs #N`.
- **Без идентификаторов моделей** в коммитах и PR. Роли называть ролями: «агент-разработчик компонентов».
- Подписаться на события PR. Поставить запасную проверку через ~45 минут.

## 3. Эталоны и учитываемый QA

**Меняется вид** (CSS, тексты, новые истории) → сразу после открытия PR запустить `qa-baseline.yml`:
`run_workflow`, `ref: main`, `inputs: { ref: <ветка> }`. Не ждать красного QA — он и так будет красным.

После коммита эталонов от `github-actions[bot]`:

- Если baseline сам ставит check-runs (`qa`, «Play-тесты историй») на новый SHA (#225 п. 1), больше ничего делать не нужно.
- Иначе: `pull_request`-прогон на бот-коммите стоит в `action_required` — сделать ему `rerun_workflow_run`. Дубль `workflow_dispatch` отменить (`cancel_workflow_run`).

**Не пушить в ветку, пока идёт baseline:** его push упадёт. Если пушить всё же нужно — отменить baseline и запустить заново.

**Вид не меняется** (логика, тесты, документация) → baseline не нужен. Учитываемый QA запускается от push.

## 4. Красный QA — разбор, не перезапуск

Открыть лог job (`get_job_logs`, хвост ~150–250 строк) и найти строку `Историй N · … · ошибок X`.

| В отчёте                                                               | Что делать                                                                                                                                                           |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| только `визуальная разница` / `нет эталона` на коммите **до** baseline | ожидаемо — ждать baseline                                                                                                                                            |
| `визуальная разница` **после** baseline                                | нестабильный кадр. Play-истории и так `no-visual`, если нет тега `visual`: снять `visual` (или пометить `no-visual` историю без play) и удалить эталоны |
| `лишний эталон` у play-истории                                         | история стала no-visual (play без `visual`) — удалить её эталоны или `--update-baseline`; скриншот нужен — тег `visual`                                         |
| `axe: …`                                                               | найти историю: `npm run qa -- --no-docker --only=<префикс>` (или `qa:changed`). Если это известное нарушение — запись в `KNOWN` (`scripts/qa/run.mjs`) со ссылкой на issue, без обходов |
| `спека` / `концентричность` / `край`                                   | баг кода или устаревшая спека — исправить, спеку менять только по Figma                                                                                              |
| сборка iOS / Android                                                   | сгенерированные имена (`npm run tokens`), см. историю #213                                                                                                           |

«Флейк» — не причина. Перезапуск без правки допустим один раз и только если job умер до тестов.

## 5. Мерж

- Только когда все check-runs на **текущем** head зелёные и нет конфликта.
- `merge_pull_request` с `merge_method: merge` и `expectedHeadSha` — **полный 40-символьный SHA**, короткий не принимается.
- Порядок при общих файлах: тот, от кого зависят другие, мержится первым; второй делает `merge origin/main`, проверки и, если нужно, baseline заново.

## 6. После мержа

1. Комментарий в issue: что вошло (коротко) и что осталось → в какой issue.
2. Отписаться от событий PR, удалить запасную проверку.
3. Удалить worktree агента: `git worktree remove --force …` и `git branch -D worktree-agent-…`.
4. Если ветка держала замок Figma — снят ли он в #6.

## Ловушки Figma API (чтобы не тратить круги)

- Заливку-узор (PATTERN) Plugin API не записывает — ни новую, ни копию. Обход — клон узла, где узор уже есть.
- Настройки показа оверлея (позиция, затемнение, закрытие по тапу вне) только для чтения — это ручная правка в панели Prototype.
- Ширину и размер вложенного экземпляра внутри экземпляра иногда нельзя переопределить: вызов проходит молча, значение не меняется. Проверять чтением после записи.
- Координаты сравнивать относительно кадра, не абсолютные: `absoluteTransform` разных кадров несопоставим.
- Перед записью — найти страницу узла. Archive, Raw, Animations и Prod не трогать, даже через переопределения экземпляров.
- Figma MCP — один вызов за раз. Скриншоты — только светлая тема.
