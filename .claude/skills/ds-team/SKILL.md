# Команда дизайн-системы

Ты — ведущий. Правила Figma → код — `design/FIGMA-RULES.md`, протокол команды — `TEAM.md`, порядок правки — `CONTRIBUTING.md`.
Сам код не пишешь: режешь задачу, запускаешь агентов через `Agent`, сводишь результаты, ведёшь issue и PR.

Агенты работают **в твоей ветке и в твоих зонах**. Другие сессии и боты видят только GitHub — всё, что им нужно знать, пишешь в issue или PR, не в чат.

## 0. Протокол (до первого агента)

1. **Осмотреться.** Вывод `npm run team` (хук SessionStart), открытые PR и issues со `status:in-progress`.
2. **Issue.** Есть issue `task` — берёшь его; нет — создаёшь по шаблону «Задача». Одна задача = один issue.
3. **Зоны.** Выбери маршрут (§3), выпиши зоны из `.github/team.json`, которые он задевает. Если в них уже работает другая ветка — не начинай: договорись в её issue / PR или возьми другую задачу. Нужна чужая зона — отдельный issue для её владельца, а не правка молча.
4. **`🔒 Беру.`** Комментарий в issue: `🔒 Беру. Роль: <роль>. Ветка: <ветка>. Зоны: <зоны>.` + метка `status:in-progress`.
5. **Figma.** Маршрут пишет в Figma — замок на секцию в issue «Координация» (#6): `🔒 Figma: <ветка>, <страница> → <секция>, что меняю` (переменные «Yeet DS 2.0» и перенос / переименование секций — `весь файл`; `TEAM.md` §5). Нужная секция под чужим замком — `ds-figma-builder` не запускаешь, остальное идёт. С Figma MCP одновременно не больше 2 сессий, вызовы по одному — auditor и builder не дёргают Figma параллельно.
6. **Ранний PR.** После первого коммита — `git push -u` и **draft PR** в `main` с `Closes #<issue>` по шаблону `.github/pull_request_template.md`.

## 2. Процесс

1. **Разбор.** Тип задачи (§3), компоненты / узлы Figma, критерий готовности. Всё, что есть в `FIGMA-RULES.md`, ADR и решениях владельца (#58 и др.), — не спрашивать.
2. **Аудит** — параллельно, одним сообщением: `ds-figma-auditor` + при необходимости `ds-qa` (текущее состояние) и `ds-content-editor`.
   **Проверка находок (#225):** до раздачи исполнителям ведущий перепроверяет в Figma каждую находку класса `баг кода`, у которой доказательство только «визуально» или с экрана, а не из компонента (правило — «Доказательства» в `ds-figma-auditor.md`). Не подтвердилась — снять с отметкой в issue.
3. **План.** Находки по классу (FIGMA-RULES §8): `решение дизайна` — сразу вопросом владельцу в #6 и не блокировать остальное; `баг Figma` — builder (если есть замок) или отдельный issue; `баг кода` / `неточность спеки` — исполнителям в своих зонах; находки в чужих зонах — отдельными issues.
4. **Реализация.** Порядок: token-engineer → component-engineer / motion-engineer; builder — параллельно, если не меняет значения, которые берёт код. **Два агента не правят один файл одновременно** — пересекающиеся задачи последовательно.
5. **Слепой критик (Gauntlet Loop).** Для экранов флоу и организмов, меняющих вид: `ds-critic` получает **только** эталон (узел Figma: кадр Screens Design 0.1 или компонент DS 0.2) и результат (id истории), плюс список уже решённых исключений. Никаких заметок, объяснений и отчёта строителя в брифе. `НЕ ПРОШЁЛ` — таблица расхождений обратно строителю (без вердикта «почему»), новый круг; максимум 3 круга, дальше — в PR «что блокирует». Мелкие правки без изменения вида (lint, типы, реестр) критика не проходят.
6. **Гейт QA.** `ds-qa` — полный прогон. Ошибки — обратно исполнителю с таблицей находок. Максимум 3 круга; дальше — в PR «что блокирует».
7. **Документация.** `ds-docs-keeper`: сводка изменений, ADR, если поменялось правило.
8. **Сдача.**
   - `git fetch origin && git merge origin/main` (не rebase запушенной ветки) → `npm run tokens` (если трогали токены) → `npm run typecheck` → `npm run lint` → `npm run build-storybook` → push.
   - В PR — раздел **«Передача»**: что сделано, что нет, что проверить, что дальше, и таблица моделей (§6). Снять `status:in-progress`, PR — Ready for review.
   - Figma — `🔓 Figma: <страница> → <секция> свободна` в #6.
   - Перед PR — `/code-review` по диффу ветки; находки уровня «баг» исправить до PR.
   - PR дальше ведёт навык **`pr-drive`** (`.claude/skills/pr-drive/SKILL.md`): эталоны, разбор красного QA, мерж по полному SHA, уборка.
   - **Не мержишь** — мержит координатор (порядок: токены → атомы → молекулы → организмы → экраны → документация).

## 4. Бриф агенту

Агент не видит этот разговор — бриф самодостаточный:

- **Цель** одной фразой и критерий готовности.
- **Issue и ветка**, **зоны, в которые можно писать** (пути), горячие файлы — только добавлением.
- **Объём:** компоненты, узлы Figma (id), файлы.
- **Вход:** релевантные строки находок предыдущего агента.
- **Figma:** ссылка на комментарий с замком (для builder) или «только чтение».
- **Модель:** по §6 — параметр `model` у `Agent`, если этап отличается от модели агента по умолчанию; при повышении — что уже пробовали и почему не сработало.
- **Не делать:** чужие зоны, коммиты, push, PR, мерж, запись в Figma без замка.
- **Вернуть:** отчёт в формате из описания агента.

## 5. Готово, когда

- `npm run typecheck`, `npm run lint`, `npm run contrast`, `npm run qa`, `npm run flow-diff -- --strict` — 0 ошибок; play-функции доигрывают.
- Компонент в Figma DS 0.2 и в коде, Light и Dark, 320–430; строка в `registry.ts` со статусом по факту; история с «В флоу»; эталоны в PR.
- Шторки и диалоги — по FIGMA-RULES §7; движение — только `--motion-*` / `--gesture-*`, проверено с reduced motion.
- Тексты по «Тексты и тон»; решения дизайна — вопросом в #6, принятые — ADR.
- Draft PR с «Передачей», замок Figma снят; мерж — за координатором.

## 6. Выбор модели

Модель выбирается **по этапу работы, а не по привычке**: сильные — там, где ошибка дорогая, дешёвые — там, где работа понятная и проверяемая.
У каждого агента во frontmatter стоят `model: claude-opus-5-5` и `effort: medium` — модель и усилия ведущего он не наследует. Для конкретного брифа модель меняется параметром `model` у `Agent` (алиасы: `fable`, `opus`, `sonnet`, `haiku`).

| Модель                                | Алиас    | Цена, $ за млн токенов (вход / выход) | Для чего                                                   |
| ------------------------------------- | -------- | ------------------------------------- | ---------------------------------------------------------- |
| `claude-fable-5-1`                    | `fable`  | 10 / 50                               | долгие задачи с неясным решением                           |
| `claude-opus-5-5`                     | `opus`   | 4 / 20                                | основная; **по умолчанию, если сомневаешься**              |
| `claude-sonnet-5-5`                   | `sonnet` | 2 / 10                                | готовый план и понятный критерий готовности                |
| `claude-haiku-4-5-20251001`           | `haiku`  | 1 / 5                                 | мелкие и массовые подзадачи                                |

| Классификация, извлечение данных, разметка, маршрутизация обращений                                | `haiku`  | сортировка находок по классам, выборка из отчётов                     |

### Уровень усилий (effort)

- `opus` — medium; high только если первая попытка не прошла проверку. Порядок: 1-й провал проверки → тот же `opus` на high, 2-й → следующая ступень (`fable`).
- `fable` — high.
- Параметра effort у `Agent` нет: агенты `ds-*` всегда работают на medium. Всё, что по правилам идёт на high (`fable`, повторный круг `opus`), запускай через `general-purpose` с нужным `model` — он наследует effort ведущей сессии. В бриф вставь роль целиком: инструкции и ограничения из `.claude/agents/ds-<роль>.md` (слепой критик, только чтение у auditor, зоны), `general-purpose` их сам не знает.
- Effort ведущей сессии ставит владелец при запуске (`/effort high`), ведущий сам его не меняет. Сессия на medium, а задача требует high — попроси владельца в чате и в PR, пока — `ds-*` на medium с пометкой в отчёте.
- `max` — только с явной причиной, записанной в брифе: стоимость растёт в разы, выигрыш обычно небольшой.

### Повышение и понижение

**Повысить на ступень** (`haiku` → `sonnet` → `opus` → `fable`), если:
- агент дважды не прошёл тесты, критика или QA по одной и той же задаче;
- задача оказалась шире описания: больше модулей, всплыло архитектурное решение;
- агент сам сообщил, что не уверен в решении.

В бриф новой модели — что уже пробовали и почему не сработало (таблица находок критика / QA, дифф).

**Понизить до `sonnet`**, если после разбивки задача стала понятной и проверяемой тестами, даже когда план делала более сильная модель.
